# 小组分工与交接方案

> 项目：低碳校园资源循环流转桌面系统（campus-loop）
> 版本：迭代 1
> 适用课程：《软件构造》分组实验 v3

## 一、总体安排

项目按 4 轮迭代推进，总计 2~3 周。每轮结束必须满足统一的完成定义（DoD），并产出 `iterN` 标签与三份交接单。

| 轮次 | 主要目标 | 出口条件 |
|---|---|---|
| 迭代 1 | 分工、接口、数据库、可运行骨架 | `mvnw clean package` 通过，登录窗口可运行，接口冻结，`iter1` 标签 |
| 迭代 2 | 业务与数据层完整实现 + 单元测试 | 物品、收藏、流转、评价、统计全部可用，`mvnw test` 全绿，`iter2` |
| 迭代 3 | 全部界面联调 + 管理员后台 + 集成测试 | 端到端流程跑通，打包 fat jar，`iter3` |
| 迭代 4 | 重构、文档、PPT、视频 | 报告与演示材料齐全，`v1.0` |

## 二、成员分工

按"模块所有权"划分：一个人拥有一个模块内的全部文件，避免三人同时改同一个类。

### 成员 1 —— 系统设计与数据层

| 项 | 内容 |
|---|---|
| 代码所有权 | `campus-core/.../model`、`enums`、`exception`、`repository`、`config`、`logging`；`campus-dao` 全部 |
| 迭代 1 任务 | 需求规格说明书、UML 类图与两张时序图、数据库设计、`schema.sql` / `seed.sql`、实体与仓储接口、`DatabaseManager`、`AbstractJdbcDao`、六个仓储实现 |
| 测试任务 | `campus-dao` 的 `CampusDatabaseTest`（种子数据、检索、增删改、收藏、分类维护） |
| 迭代 2 任务 | 事务边界与异常映射、`DealRepository` / `ReviewRepository` 实现、索引优化 |
| 迭代 3 任务 | 数据一致性排查、数据库脚本定稿、部署说明书初稿 |
| 迭代 4 任务 | 课程设计报告主体、UML 终稿、部署说明书 |

### 成员 2 —— 业务逻辑与测试

| 项 | 内容 |
|---|---|
| 代码所有权 | `campus-core/.../service`、`util`、`query`；`campus-service` 全部；全部测试基础设施 |
| 迭代 1 任务 | 服务接口契约、`PasswordUtil` / `Validators` / `CsvUtil`、`AuthServiceImpl`、`ItemServiceImpl`、`ServiceFactory`、JUnit 测试规范与用例骨架 |
| 测试任务 | `PasswordUtilTest`、`ValidatorsTest`、`CsvUtilTest`、`AuthServiceTest`（伪造仓储），并在迭代 2 负责集成测试 |
| 迭代 2 任务 | 流转与评价业务、信用分计算策略、CSV 导出模板方法、业务层单测完善 |
| 迭代 3 任务 | 集成测试、代码走查、坏味道清单 |
| 迭代 4 任务 | 重构实施（策略模式、模板方法）、测试报告 |

### 成员 3 —— GUI、复用与交付

| 项 | 内容 |
|---|---|
| 代码所有权 | `campus-ui` 全部、`campus-app` 全部、父 POM 与各子模块 POM、`mvnw` |
| 迭代 1 任务 | Maven 多模块骨架、Maven Wrapper、登录窗口、注册对话框、主窗口与六个页签、表格模型、`Bootstrap` 组合根、shade 打包、README |
| 测试任务 | GUI 冒烟测试清单（手工执行并留截图），迭代 3 补 GUI 层自动化测试 |
| 迭代 2 任务 | 检索页、发布对话框、收藏页、流转页联调 |
| 迭代 3 任务 | 管理员后台、端到端联调、fat jar 打包 |
| 迭代 4 任务 | 设计模式整合说明、PPT、演示视频、提交记录整理 |

## 三、交接机制

交接不是"扔文件"，而是三个可验证的约定。

### 3.1 接口冻结

迭代 1 结束时冻结 `campus-core` 中的内容：

- 实体字段（`model` 包）
- 枚举取值（`enums` 包）
- 仓储接口方法签名（`repository` 包）
- 服务接口方法签名（`service` 包）

此后任何签名变更必须：

1. 先在 `docs/设计/接口契约.md` 登记变更条目（版本、原因、影响范围）；
2. 在当前轮的交接单中列明；
3. 同步通知另外两人，在评审会上确认。

### 3.2 交接单格式

每轮每人提交一份 `docs/交接/迭代N-成员X-交接.md`，固定五段：

1. **已完成**：文件清单 + 对应需求编号
2. **未完成 / 留给下一轮**：明确写清为什么没做
3. **接口或数据结构变更**：签名变更、字段增删、SQL 变更
4. **已知缺陷与绕过方式**：能复现就写复现步骤
5. **给下一棒的验证步骤**：可复制的命令，别人照着敲就能验证

### 3.3 交接验收

下一棒按交接单第 5 段原样执行命令。全部通过才允许上一棒的分支合并进 `main`。验收过程记入 `docs/协作/小组会议记录.md`。

## 四、完成定义（DoD）

每轮结束时，以下全部满足才算完成：

- [ ] `./mvnw clean package` 成功
- [ ] `./mvnw test` 全部通过，无跳过
- [ ] 新增代码有对应测试或说明为何无测试
- [ ] 文档与代码同步（接口变更已登记）
- [ ] 提交信息符合 `类型(范围): 中文描述` 规范
- [ ] 交接单已提交
- [ ] 分支已合并并打 `iterN` 标签

## 五、分支与合并规则

| 项 | 规则 |
|---|---|
| 主干 | `main`，始终可构建 |
| 分支命名 | `iterN/mX-<主题>`，例如 `iter1/m1-design-data` |
| 提交者 | 三个成员的产出由同一台机器实现，用 `git -c user.name=... -c user.email=...` 区分作者 |
| 合并方式 | `git merge --no-ff`，保留合并提交，便于看出三条开发线 |
| 标签 | 每轮 `iterN`，交付版本 `v1.0` |
| 冲突处理 | 谁的分支冲突谁解决，解决后重新跑一遍 DoD |

## 六、沟通约定

- 每轮开始：30 分钟计划会，确认本轮范围与接口
- 每轮结束：30 分钟验收会，逐条执行交接单的验证步骤
- 日常：问题先记录在 `docs/协作/小组会议记录.md` 的"待办"里，不在聊天里口头约定
- 阻塞超过半天：直接升级给其他成员，不自己硬扛

## 七、风险与应对

| 风险 | 应对 |
|---|---|
| 三人改同一文件产生冲突 | 按模块所有权划分，跨模块修改必须先在评审会提出 |
| 接口临时变更打断下游 | 接口冻结 + 变更登记；下游用接口编程，不直接依赖实现 |
| 时间被压缩 | 迭代 1 交付可运行骨架，后续每轮都能演示 |
| 单账号推送导致 GitHub 只显示一人 | 邀请队友为 collaborator，各自推送自己的分支；本地用 `git shortlog -sne --all` 证明分工 |
