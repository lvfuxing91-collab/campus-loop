# 迭代2交接单——成员1（系统设计与数据层）

- 对应分支：`iter2/m1-deal-review-dao`（流转评价仓储与共享事务）、`iter2/m1-stats-caliber`（统计口径与索引），两分支均已合并至 `main`。
- 交接对象：成员2（业务与测试）、成员3（GUI与交付）。

## 一、本轮完成内容

### 1. 共享事务连接

| 位置 | 变更 |
|---|---|
| `DatabaseManager` | 新增线程绑定的事务连接与 `currentTransactionConnection()`；`inTransaction` 在事务中把连接绑定到当前线程，嵌套调用复用最外层事务 |
| `AbstractJdbcDao` | 所有公共方法改为经 `withConnection` 执行：事务中复用绑定连接且不关闭，事务外新开连接并在结束后关闭 |

效果：一次 `inTransaction` 回调内的多个仓储写入共用同一连接，可以整体提交或回滚。仓储接口签名没有变化，业务层不需要感知连接来源。

### 2. 流转与评价仓储

| 类 | 说明 |
|---|---|
| `DealRepositoryImpl` | 实现 `DealRepository` 全部 7 个方法：插入、更新、按ID/用户/物品查询、总数与按状态计数 |
| `ReviewRepositoryImpl` | 实现 `ReviewRepository` 全部 5 个方法：插入、按被评价人/流转查询、是否已评价、平均分 |
| `DealMapper` | 联结 `items` 与两次 `users`，补齐 `itemTitle`、买卖双方昵称；`completed_at` 可空 |
| `ReviewMapper` | 联结 `users` 补齐评价人昵称 |
| `DaoFactory` | 新增 `dealRepository()` 与 `reviewRepository()` |

`findByUser` 同时匹配买家和卖家；`findByDeal` 按评价时间升序；`averageRating` 在无评价时返回 0。

### 3. 测试

`CampusDatabaseTest` 新增 10 项用例，覆盖：

- 流转插入回读、展示字段（物品名、双方昵称）、可空成交时间
- 按用户、物品、状态查询与计数
- 状态更新与成交时间写入
- 无效买家被外键拒绝
- 评价插入、按人/按交易查询、平均分
- 同一交易同一评价人重复评价被唯一约束拒绝
- 评分超出 1～5 被 CHECK 约束拒绝
- 事务回调失败时两个仓储的写入全部回滚
- 事务成功时两个仓储的写入一并提交
- 事务外调用仍正常持久化

当前全项目 96 项测试通过（core 21、dao 60、service 15），`mvnw clean package` 成功。

## 三、接口与数据变更

- `DealRepository` 新增 `countCompletedByCategory()`，已在[接口契约](../设计/接口契约.md)登记；其余仓储接口签名未变。
- `StatsServiceImpl` 构造参数增加 `DealRepository`，`ServiceFactory` 同步调整。服务层与组合根属成员2、成员3范围，需二人确认。
- `DaoFactory` 新增 `dealRepository()`、`reviewRepository()`。
- 数据库结构未变，仍是 8 张表；显式索引由 9 个增至 11 个。

给成员2的调用约定：

1. 需要多表原子写入时，把相关仓储调用放在同一个 `database.inTransaction(...)` 回调内，不要在外层再手工开连接。
2. 事务内抛出的 `RuntimeException` 会回滚并原样向上传递；其他受检异常回滚后包装为 `DataAccessException`。
3. 事务内不要自行 `close()` 传入的连接；仓储已负责复用。
4. `Deal.status`、`Review.rating` 的合法取值由业务层先校验，数据库约束只作为最后防线。
5. `DealRepository.findByUser` 同时返回作为买家和作为卖家的记录，界面按 `buyerId/sellerId` 区分角色。

## 四、已知限制

- 异常消息已完成脱敏：用户只看到按约束类别生成的中文提示，SQL 与原始异常保存在 `getDetail()` 中仅写日志。验证方式见第五节。
- `SqlErrors` 依据 SQLite 约束文本匹配（unique / foreign key / check / not null）。若更换数据库驱动或错误文案，需要同步调整匹配规则。
- 事务连接绑定在当前线程；若后续引入多线程写库，需要扩展为显式传递连接或连接池方案。
- `Deal` 与 `Review` 的查询依赖 `JOIN items/users`，若关联数据被删除则记录不再返回；当前外键为级联删除，正常情况下保持一致。
- `update` 不返回受影响行数，业务层不能仅凭无异常判断记录是否存在，更新前应先 `findById`。
- 金额仍以 REAL 存储，精度问题与本轮无关，沿用既有约定。
- 物品状态与流转状态目前没有数据库层的一致性约束，只能由业务层保证；迭代3 用一致性校验查询补上检查。

## 五、验证步骤

在项目根目录、已配置可用 JDK 的终端执行：

```bash
./mvnw -B -ntp -pl campus-core,campus-dao -am test
```

预期：core 21 项、dao 60 项通过，失败、错误、跳过均为 0。

```bash
./mvnw -B -ntp clean package
```

预期：全项目 96 项测试通过，生成 `campus-app/target/campus-loop.jar`。

手工验证事务回滚（无需界面）：运行 `CampusDatabaseTest` 中的 `transactionRollsBackWritesFromMultipleRepositories`，确认事务内先插入的流转记录在异常后不存在。

使用独立目录启动，保留原有数据：

```bash
java -Dfile.encoding=UTF-8 -Dcampusloop.db=target/member1-check/campus.db -Dcampusloop.home=target/member1-check -jar campus-app/target/campus-loop.jar
```

验收点：登录与物品检索保持原有表现，说明数据层改造未影响已有功能。统计页此时显示“完成流转 0、减排 0.0”，属预期行为。
