## 三、成员 1/2身份核对与提交建议

远端已经存在不同作者的迭代 2提交。两位成员应先确认这些提交是否就是本人账号产生的：

```bash
git fetch origin
git log origin/main --format='%h %an <%ae> %s'
git config user.name
git config user.email
```

若历史提交已是本人身份，只需保留压缩包和提交记录作为交付证据，不再创建重复代码提交。若课程要求补充本人确认，可从最新 `origin/main` 新建证据分支，仅增加本人签名的交付确认文档后发起 PR；不要重新覆盖代码文件。

## 四、成员 3提交步骤

成员 3在提交前确认：

```bash
git config user.name
git config user.email
git diff --check
./mvnw clean package
./mvnw test
```

本机无 JDK 时，应在有 JDK 的机器或 CI 中补做 Maven 验证，再合并 PR。建议提交信息：

```text
feat(ui): 补全物品详情筛选与统计导出
```

## 五、合并与发布门禁

1. PR 基线必须是最新 `main`，不得包含远端已有代码的回退或删除。
2. 全量测试通过后再合并成员 3 PR。
3. 人工验收完整链路：检索 → 详情 → 意向 → 接受 → 完成 → 评价 → 统计导出。
4. 三位成员核对作者身份、交接单和交付清单。
5. 验收通过后再创建 `iter2` 标签；若标签已存在，不覆盖、不强推，先核对目标提交。

## 六、回滚策略

- 成员 3功能集中在独立 PR，可通过 GitHub Revert 回滚，不改写 `main` 历史。
- CSV 导出失败不影响统计查看；详情入口异常时仍保留列表页原有快捷意向入口。
- 任何合并冲突都以最新远端实现为主，逐项迁移增量，不整文件覆盖。
